## Notes

- **A place for club-less photographers** — Not only an on-ramp for the app. A club member gets something back through the club; a federation member with no club pays the same and belongs to nothing, so the federation's value proposition is weakest exactly here, and these members have been treated as strays. The app can supply what they lack — a way to find each other, if they want to. The aim is to help them get organised, with a coordinator per district, repeating what one volunteer already did in one district and submitted as a list. Cheap, partly working already, and its most useful advocate would be describing his own situation rather than endorsing someone else's project.

- **Exhibitions near you** — PICKED as one of the first things to build (4 Sept 2026). Three reasons beyond the rating: supporters do not see the value when it is described, because they judge it as attendees while the value is to club officers, and a two-day build replaces the explanation with a demonstration; it reads well in release notes where infrastructure work does not; and shipping something visible creates an occasion to talk to people, which is scarce now that the federation magazine is closed to this. The only row aimed at club officers rather than at viewers or maintainers, which matters because officers decide whether a club takes part. A club runs one or two exhibitions a year, spends real money on each, and spends the preceding month pushing them through mailing lists, its own website, regional newsletters, posters and the local paper. A new distribution channel for that is worth something to them even if the app did nothing else. Demand is proven: a paid Dutch listing service charges an annual fee for roughly this, and at least one club already in our data subscribes. The structural advantage is that a listing site has to be remembered and visited, whereas every club here already has coordinates, so proximity and a home-screen reminder are natural. Organisers are not only clubs: galleries and museums run exhibitions too, so an exhibition belongs to an organization rather than to a club. The model already allows that — OrganizationType is club/museum/unknown — so a gallery is one more case, not a new concept. Worth noting this finally gives the 42 museums already in the data a purpose: they have no members and no photographs, which is why nobody would miss them today, but holding exhibitions is precisely what they do. Open question: who supplies exhibition data for an organisation that will never maintain a Level 2 file. Effort re-estimated XL to S on a written spec. Level 2 files gain a third block beside club and members, which is backwards compatible in both directions because the reader already branches on jsonRoot[...].exists(). An Exposition entity with a one-to-many link from Organization, so museums get it at no extra cost. Fields: organization, start and end date, and a poster URL shown as a plain link that opens externally, exactly like the club, photographer and Wikipedia links already on those cards. Shown as an animated marker plus next-exhibition text on the map card. Phase two adds Settings filters for distance and time horizon. The earlier XL was costing a widget, notifications and a whole new JSON level, none of which is in this spec; those are now a separate row. DECIDED: start and end date, both day granularity, no times. Club exhibitions usually run one or two days and the dates are always on the poster, but not machine readably; a museum or gallery exhibition runs for weeks, and museums come free through the Organization relationship, so a start-only model would fail exactly where duration matters most. It is also a published field in a package other software may consume, so it is modelled for the domain rather than for the current screen. Two useful side effects: nobody travels to something that closed yesterday, and records expire by themselves rather than needing the pruning Data#39 exists for. STILL OPEN: do not let the poster carry the address and time alone, since both club-hosted URLs in the data return 404 today. LAYOUT: the map card is already four blocks deep and MapsViewInfo is crowded, so the preferred placement is for the exhibition line to displace MapsViewRemark while it runs; permanent context gives way to time-critical content at no net height, and the remark returns afterwards. Note that notifications for these belong with follow-people rather than here: following someone is what makes an alert wanted rather than an interruption.

- **Follow the clubs and photographers you like** — THE PREREQUISITE FOR BOTH NOTIFICATION-SHAPED FEATURES, added 4 Sept 2026 after noticing it had no row at all: an earlier follow-a-club row was merged away and no ticket for it could be found in 400 issues. A widget and a notification are not alternatives to each other, they are two surfaces on this. Without a follow list a widget is decoration and a notification is spam; Glass.photo's widget works precisely because it shows only the people you follow, and they run both surfaces off it. FOLLOWING IS THE OPT-IN, which removes a design problem rather than adding one: there is no separate notification consent flow to invent, because the user has already said who they care about. SEQUENCE, cheapest first, each earning the next: the follow list, then the widget which is nearly free once the list exists since it is a read-only view of data already held, then notifications, which still need scheduling, permission handling and a judgement about what merits interrupting someone. That last part is the expensive bit and is deliberately not specified yet. On utility alone a notification beats a widget, because an exhibition is time-bound and a widget only helps someone who glances at the right moment, but it is far riskier: an uninteresting widget costs nothing, while one unwanted notification gets notifications switched off permanently and there is no second attempt. Glass uses a distinctive camera shutter sound, which is cheap and effective differentiation and worth stealing when the time comes. EFFORT RE-ESTIMATED M BACK TO S. The M rested on followed things vanishing between data loads, but that solves itself: what you follow lives in UserDefaults, what exists lives in the JSON, and merging the two simply leaves some entries unresolved. How to present those is a display decision, grey them out, drop them, or keep them in case the club returns, not the obsolete-flag machinery in Core Data. The residual risk is choosing the identifier, since names change, which is the same identity problem as married names and infix capitalisation elsewhere in this file, and clubs at least have a stable nickName. IT IS ALSO A LOADING POLICY, NOT ONLY A DISPLAY FILTER. The app may reasonably want to load only the clubs someone follows, which makes this an input to #803 rather than a personalisation nicety, and raises its worth well above what the description suggests. Whoever rates this should weigh that: the row reads like a convenience and behaves like infrastructure. WHY GEOGRAPHY IS NOT A SUBSTITUTE: an exhibition alert can filter on distance and date cheaply, but someone may still care about a club they left behind when they moved. Affinity is not derivable from location, which is the case for keeping an explicit list at all. On the distinctive sound: worth having, not worth copying. Glass uses cat and dog sounds for their cat and dog categories, which may be a little cute, and lifting their shutter sound literally would be poor form given the teams know each other. THE AUDIENCE IS WIDER THAN PHOTOGRAPHERS, and this may be the strongest argument for the row. Following a person, not a club, is the primary case, and the people who most want it are friends and family. A daughter in Australia following her father's portfolio is the same phenomenon as Dutch expatriates reading Dutch newspapers online: affinity survives any distance, and no proximity filter will ever reconstruct it. That audience is niche per member and large in total, since every member has some, and it needs no data of its own, which makes it the cheapest distribution the project has. The member does the inviting. It also answers the cold-start difficulty directly: these are users who arrive with a reason to care and who cost nothing to serve. TWO DESIGN CONSEQUENCES. Distance must not be a hard filter anywhere in this feature or its surfaces, or the overseas follower receives nothing at all. And the reader-facing wording should lead with following a person rather than a club, because clubs are what this project is organised around but a person is what a non-photographer follows. PERSON FOLLOWING IS STRONG, CLUB FOLLOWING WEAKER BUT REAL. Parents following their son do not want his whole club, unless they occasionally drive over to see the work. The club case is thinner but genuine: someone who left a club after thirty years, or who moved a hundred kilometres away and is now recorded as a former member, may still want to know what that club is doing. Membership history spans clubs and decades, so a follow list keyed only to current membership would miss the strongest cases.

- **Start from your website** — OPEN, needs thought: everything below concerns LEVEL 3 scavenging, images per photographer. LEVEL 2 scavenging, the members of a club, is a different problem and probably needed earlier, since it is what turns a listed club into a populated one and that is the twelve-of-ninety-two gap. It cannot use either technique described here. Browser instrumentation works for images because images are fetched resources that can be observed on the network; a name is not a resource and produces no event. Static parsing does not help either, because names sit in arbitrary layout as prose, lists, tables or cards, and Dutch names then have to be split into given name, infix and family name. Expertises are almost never present on club sites in any standard form. So the conclusion inverts: for Level 3 a model is optional, for Level 2 it is where one would actually earn its keep. Note also that the Fotobond holds member data, which may be a better source than any website. Scope is LEVEL 3, images per photographer. ACCEPTED CONSTRAINT: the input is one URL for one club member, so the image-to-member association is given by which page you pointed at and the matching problem disappears. Common in practice, since a portfolio page usually shows one photographer. Approach is browser instrumentation rather than parsing: a headless browser loads the page and records every response with an image content type, which collapses all page shapes into one case and is agnostic to whatever produced the images, including a backend-generated page such as WordPress. Icons and logos are filtered mechanically by size, by recurring across two pages of the same site, and by path, so a paid model connection is optional and only for the residue. STRICTLY EDIT TIME: output is JSON, so nothing at app launch or at site generation depends on it. It therefore need not be Swift, need not use the Data library and need not run on macOS; as a separate tool whose output the editor imports, it runs on Windows too. Cost is the variety of real sites, cookie overlays and scroll-triggered lazy loading, not the browser work. Dick's tool covers this ground already, using cheerio, which is static-only and takes the img src rather than the enclosing anchor's href, so it captures thumbnails. CLICK-THROUGH GALLERIES, EFFORT RECONFIRMED AT M BUT CONDITIONAL. A gallery where the next image is fetched only on a click is not covered by passive listening, since waiting reveals nothing. Three tactics, most robust first. One, sniff the manifest: most gallery generators fetch a json or xml list of every image before showing any, Juicebox config.xml being the case the iOS app already parses, so one response yields the whole set with no interaction. Two, drive the page with repeated ArrowRight presses, which most lightboxes bind, avoiding a per-site next-button selector, stopping when a press produces no new request or the first URL reappears. Three, stepwise scrolling for lazy-loaded grids, which was already inside the estimate. Together these turn one universal scraper into a dispatcher plus a few per-generator recipes plus a generic fallback, and that is what could push it to L. It stays M only on an explicit scope decision: the tool is best effort and is allowed to report that a page defeated it, rather than aiming for full coverage. That is affordable because the level2-editor exists to correct its output, and expensive to reverse later, since promising completeness makes every bespoke gallery a bug report. Cycle detection is the underrated cost, because carousels preload neighbours, wrap around, and vary URLs with cache-busting query strings. CONDITION SETTLED, M STANDS. He states the policy explicitly: handle 80 percent first, then 90, then 95, driven by what is actually encountered, since every exception involves his review of both the approach and the correctness of the outcome anyway. So best effort is the intended design, not a concession. The one design requirement that makes incremental coverage converge rather than drift is that failure must be visible. The dangerous case is not zero images, which is obvious, but plausible partial output, eight of thirty, or thumbnails passed off as full images, which is precisely Dick's bug. The tool should therefore report image count, pixel dimensions and whether a manifest was found, so his review has something to check against. POPULATION SHAPE, MEASURED 4 Sept 2026. Level 3 special cases are per site, not per URL: 212 portfolio URLs across 17 level2 files resolve to only 14 distinct hosts, because a club's members share one website and one gallery generator. A census of those 14, asking which generator and whether it publishes a manifest, is an hour of work and tells you directly how many recipes buy 80 percent. Level 2 has no such amplification: 193 club websites are 192 distinct hosts, one per club. The useful Level 2 census therefore asks a different question, not how many recipes but what fraction of club sites list their members publicly at all, since that number could settle the feasibility of Level 2 scraping outright. SHIPS IN TWO PHASES, decided 5 Sept 2026. The engine is one thing; how it reaches a club is two. PHASE 1, level2-on-request, also called level2-as-a-service: someone on our side, not necessarily Peter, runs the tool for a club that asked and sends back a draft to correct. Human in the loop, roughly a day's turnaround including weekends, which beats most commercial replies. It needs no editor, no server and no button beyond the one in claim-your-club, and the tool for it exists at scripts/scavenger/. PHASE 2, self-service: the club runs it themselves from inside the level2-editor and never waits for anybody. That is the version that scales, and it depends on #833. The phases are not separate rows. The effort column measures build time and phase 1 has almost none left, while its real cost is per club and recurring, which this column cannot express. Worth revisiting only if testers should be asked to choose between being served and serving themselves, which is a genuine question but not one an effort figure can carry. - **Suggestions from your own website** — Distinct from level2-autofill, which starts a club from nothing. This one compares a club that already has data against its own website and proposes differences. Measured 4 Sept 2026 across all 193 federation club sites: 82% Jaccard agreement between stored data and websites on the seven clubs where both exist, with the residual being genuine disagreement between two independently stale sources rather than extraction error. TWO REASONS THIS MODE IS EASIER THAN COLD START. First, ground truth bounds the errors: the output is a short list of differences a human checks in a minute, not a proposed roster, so noise that would be unusable in cold start is merely ignorable here. Second and stronger, the stored roster is a vocabulary that makes partial evidence resolvable at all. On one club's members page eleven bare given names each resolved to exactly one current member; without the roster 'Bram' is unusable, with it 'Bram' is a member. THE VALUE IS THE WARNING, NOT THE ACCURACY. Reviewers spot a name that should not be there and miss a name that is absent, because attention goes to what is on the page. So the finding no human review catches is 'on your website, not in your data'. Do not treat the agreement score as a target: it can be raised by suppressing uncertain findings, and each suppressed finding is a warning nobody gets. EFFORT RE-ESTIMATED S TO M as the scope grew during discussion. The comparison itself is S, since the extraction already exists and a diff against stored JSON is small. What makes it M is being usable more than once: a decision recorded per finding, with expiry driven by a fingerprint of the evidence rather than by time, so a dismissal lapses when the club's page changes instead of silently suppressing a warning that has become valid again. Cadence is annual at minimum, since membership churn clusters around 1 January, but a monthly scheduled run is cheap and keeps the findings honest. THEME IS ARGUABLE: filed under keeping it working because from a reader's point of view the promise is that their page stays right, but it could sit under getting more clubs on board, since it also manufactures the reason to make contact and shares all its machinery with the editor. Design recorded on #835 (extraction and the two modes), #833 (the editor, the three-way comparison and the decision states) and #840 (consent, and the rule for what may be stored where). No dedicated ticket yet.

Sequence: build and maintain the macOS version; if in a couple of years a web version proves unavoidable, add it using the macOS version as an executable specification, ported by someone who does web applications with full access to the original. That port is unusually attractive contributor work, having a precise spec, a clear finished state, and no need to understand the rest of the system. To make it cheap, keep validation and JSON generation in plainly readable functions rather than inside SwiftUI views, so the port is a UI rewrite rather than archaeology. Note the scavenger stays cross-platform regardless, since it only emits JSON. Absorbs the submission step: the point is that a maintainer never touches GitHub. Interim workaround while there is no editor: the author mails the file in, which works but loses the public authorship that shows other people are involved.
- **Show me what I care about** — REWRITTEN — was a performance row, is really about relevance Ships in two steps: picking a few favourite clubs so the app opens on them is the cheap first version and can land on its own; choosing people and kinds of photography as well is the full one.
- **Every portfolio shown the same way** — Goes to the project's stated reason for existing. The built-in Readme opens with "displays selected photos ... in a consistent, accessible manner, while minimizing distractions", and argues that web sites are less suitable because they are cluttered by browser controls and other content. Portfolios are currently satisfied by rendering exactly such a web site in an embedded browser, so presentation is at the mercy of each club's site — some show the selected photo over a backdrop of others. It also blocks a whole category: nothing at the level of an individual photograph is possible today, so no photo counts in the statistics and no finding a similar image. (Tapping a club or photographer link is separate: that does open an external browser.) The club's gallery XML is parsed only to extract one thumbnail; Level 3 should use it as seed data instead of rendering the page.
